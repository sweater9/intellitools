Kubernetes (Container Orchestration)

platformfreshness: volatilesources not yet verified

Kubernetes runs and manages containers across a cluster of machines: scheduling them, restarting failures, scaling, rolling out updates and wiring up networking and configuration.

Short answer: Kubernetes (K8s) is a container orchestrator: you declare the desired state (Deployments, Services, config) and the control plane keeps the cluster matching it. It solves scheduling, self-healing, scaling and rollout at the cost of real operational complexity — use a managed service and start small.

What is it?

Docker packages one app into a container. Kubernetes is what runs hundreds of those containers across many machines: it decides where each one goes, restarts it if it crashes, adds copies when traffic grows and rolls out new versions without downtime. You describe what you want in YAML files, and Kubernetes works to make reality match.

Also known as: k8s, kubectl, kubernetes basics, helm chart, helm charts, helm, container orchestration, kubernetes cluster.

Technical definition

A cluster has a control plane (API server, etcd, scheduler, controller manager) and worker nodes (kubelet, container runtime, kube-proxy). Core objects: Pod (one or more containers sharing network and storage), ReplicaSet/Deployment (stateless replicas and rolling updates), StatefulSet (stable identity and storage), DaemonSet, Job/CronJob, Service (stable virtual IP and load balancing), Ingress/Gateway (HTTP routing), ConfigMap and Secret, PersistentVolume(Claim), Namespace, and RBAC. The Horizontal Pod Autoscaler scales replicas on metrics. Helm packages manifests as charts with values. The model is declarative and reconciliation-based; it descends from Google's Borg (Burns et al., 2016). Release cadence, API deprecations and supported versions change several times a year.

Entity type: platform · Freshness class: volatile.

When should I use it?

Use it when you run many services or replicas that need self-healing, scaling and zero-downtime rollouts, or when your organisation already standardises on it. Prefer simpler hosting (a PaaS, serverless, or one VM with Docker Compose) for small or early-stage workloads.

Prerequisites and related concepts

Understand these first: Containers, Docker.

Related concepts: CI and CD, AWS Fundamentals for Application Developers, Azure Fundamentals for Application Developers, Google Cloud Fundamentals for Application Developers, Model Serving and Inference Infrastructure, Ray (Distributed Computing for AI), MLOps (Machine Learning Operations), vLLM, Environment Variables.

Implementation patterns

  • Declare everything in version-controlled manifests or Helm charts and deploy through CI/CD (GitOps).
  • Set CPU and memory requests/limits on every container so the scheduler and autoscaler behave.
  • Use readiness and liveness probes so traffic only reaches healthy pods.
  • Use a managed control plane (EKS, AKS, GKE) rather than running your own.
  • Isolate teams and environments with namespaces, RBAC and network policies.
  • For GPU model serving, request GPUs explicitly and keep model weights on a persistent or cached volume.

Technologies and frameworks

Commonly associated: kubectl, Helm, Kustomize, managed services (EKS, AKS, GKE), Ingress controllers, Prometheus, NVIDIA device plugin for GPUs, KubeRay, KServe. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Make sure the app already runs well as a container and reads its config from environment variables.
  2. Create or choose a managed cluster and connect with kubectl.
  3. Write a Deployment with resource requests/limits and probes, and a Service to expose it.
  4. Put config in ConfigMaps and secrets in Secrets or an external secret manager.
  5. Add an Ingress for HTTP routing and an HPA if load varies.
  6. Deploy through CI/CD, and watch logs, events and metrics.

Common failure modes

  • Adopting Kubernetes for a small app that a single container host or a PaaS would run more simply.
  • No resource requests/limits, causing noisy neighbours, evictions or OOM kills.
  • Secrets stored in plain manifests (Secret values are only base64-encoded by default).
  • Probes misconfigured, so healthy pods are killed or unhealthy pods receive traffic.
  • Using the latest image tag, making rollouts and rollbacks unpredictable.
  • Falling behind on version upgrades until API removals force a painful migration.

Troubleshooting

  • Pod stuck in CrashLoopBackOff — Read kubectl logs (add --previous) and kubectl describe pod; fix the startup error, missing config or failing probe.
  • ImagePullBackOff or ErrImagePull — Check the image name and tag, registry credentials (imagePullSecrets) and network access to the registry.
  • Pod Pending — Run kubectl describe pod; usually insufficient CPU, memory or GPU, an unsatisfied node selector/taint, or an unbound volume claim.
  • OOMKilled — The container exceeded its memory limit; raise the limit or reduce usage, and check for leaks.
  • Service reachable inside the cluster but not outside — Check the Service type, Ingress rules and controller, and cloud load-balancer provisioning.

Contrasted with

  • Docker — Docker builds and runs containers on one host; Kubernetes orchestrates containers across many hosts.
  • Containers — A container is the unit of packaging; Kubernetes is the system that schedules and supervises many of them.
  • CI and CD — CI/CD builds and ships changes; Kubernetes is one place those changes are deployed to.
