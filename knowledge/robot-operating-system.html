ROS (Robot Operating System)

frameworkfreshness: volatilesources not yet verified

ROS is the widely used open-source middleware and tool ecosystem for building robot software: processes (nodes) exchange messages over topics, services and actions, with libraries for navigation, manipulation, simulation and visualisation.

Short answer: ROS 2 structures a robot program as nodes that communicate over topics (streams), services (request/response) and actions (long tasks), with a DDS-based transport and tooling such as rviz, Gazebo, Nav2 and MoveIt. It is middleware and tooling, not an operating system.

What is it?

ROS is a toolbox and plumbing layer for robot software. You split a robot into small programs — one reads the camera, one plans a path, one drives the wheels — and ROS lets them talk to each other, record data, show it on screen and run in simulation. Despite the name it runs on top of Linux (and other systems).

Also known as: ROS, ROS 2, ROS2, robot operating system, rviz, gazebo, nav2, moveit.

Technical definition

ROS 2 (the current generation; ROS 1 is end-of-life) provides: nodes; publish/subscribe topics with typed messages; services; actions with feedback and cancellation; parameters; launch files; lifecycle nodes; the tf2 coordinate-transform library; and quality-of-service profiles. Transport is via the ROS Middleware Interface over DDS implementations (Quigley et al., 2009 for ROS 1; Macenski et al., 2022 for ROS 2 design). Common stacks: Nav2 (navigation), MoveIt (motion planning), ros2_control, Gazebo (simulation), rviz2 (visualisation), rosbag2 (recording). Builds use colcon; nodes are written in C++ (rclcpp) or Python (rclpy). Learned policies (Vision-Language-Action (VLA) Models, Imitation Learning (Behaviour Cloning and DAgger)) are typically wrapped as nodes. Releases ("distributions") have fixed support windows.

When should I use it?

Use ROS 2 when you need a common messaging and tooling layer for research or products involving robots, sensors and simulation. For a single microcontroller or a simple simulator experiment it may be unnecessary overhead.

Implementation patterns

  • Keep nodes small and single-purpose; define clear message types.
  • Launch systems with launch files and parameter files rather than shell scripts.
  • Develop in simulation first, then validate on hardware with safety limits.
  • Wrap a learned policy as a node that subscribes to sensor topics and publishes commands, with a conventional safety controller beneath it.
  • Record rosbags of real runs to build datasets and reproduce bugs.

Technologies and frameworks

Commonly associated: ROS 2 distributions, DDS middleware, Nav2, MoveIt, ros2_control, Gazebo, NVIDIA Isaac Sim (ROS bridge), rviz2, rosbag2, Docker. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Choose a supported ROS 2 distribution for your operating system.
  2. Work through the official beginner tutorials (nodes, topics, services, launch files).
  3. Create a workspace and package, build with colcon, and source the setup file.
  4. Simulate the robot in Gazebo or another supported simulator.
  5. Add perception, planning and control nodes; visualise in rviz2; record rosbags.
  6. Test on hardware gradually with limits and an emergency stop.

Common failure modes

  • Mismatched QoS settings so publishers and subscribers silently do not connect.
  • Wrong or missing coordinate-frame transforms (tf2).
  • Clock and simulation-time mismatches (use_sim_time).
  • Mixing ROS distributions or ROS 1 tutorials with ROS 2 code.
  • Latency or jitter from heavy inference in the control loop.
  • Running learned policies without a hardware safety layer.

Troubleshooting

  • Subscriber receives nothing — Check topic names and types with ros2 topic list/info, QoS compatibility, namespaces and that both nodes share the same ROS domain ID.
  • Robot model appears in the wrong place — Inspect the tf tree and frame names; verify static transforms and time stamps.
  • Tutorial commands fail — Confirm the tutorial matches your ROS distribution and that you are using ROS 2, not ROS 1.
  • Inference makes control laggy — Run the model in a separate node/process, lower the rate, or move it to an accelerator.

Contrasted with

  • Embodied AI — Embodied AI is the field; ROS is one widely used software framework for building robot systems.
  • Docker — Containers package and isolate ROS applications; they do not replace ROS messaging.
